# Post-MVP backlog — Life RPG

Список несостыковок и ограничений, найденных после завершения этапа 6.
Это backlog для будущих доработок: пункты ниже не реализованы.

Приоритеты:

- **P0** — влияет на корректность данных, прогресса или production-эксплуатацию;
- **P1** — заметный функциональный пробел или расхождение со `SPEC.md`;
- **P2** — UX, документация и технический долг.

## P0 — корректность и целостность

- [ ] Запретить ручное завершение квеста, пока не выполнены все обязательные шаги.
  Сейчас `completeQuest` проверяет только статус квеста, а кнопка завершения доступна
  независимо от прогресса.
- [ ] Запретить изменение шагов завершённого или архивного квеста на сервере.
  UI блокирует чекбоксы только у завершённого квеста, но endpoint toggle не проверяет
  статус квеста.
- [ ] Определить допустимость квеста без шагов. Сейчас API разрешает пустой массив,
  хотя спецификация описывает квест как цель из одного или нескольких измеримых шагов.
- [ ] Исправить период `all` на экране прогресса: `fillDailyRange` ограничен 400 днями,
  поэтому длинная история и итоговый `totalXp` обрезаются и могут не включать последние дни.
- [ ] Сделать текущую серию актуальной относительно сегодняшней даты. Сейчас она остаётся
  равной последней накопленной серии даже после длительного пропуска.
- [ ] Определить правила серии для шаблонов по дням недели. Текущий расчёт требует
  последовательных календарных дней, поэтому расписание Пн/Ср/Пт почти всегда имеет серию 1.
- [ ] Запретить или корректно мигрировать смену характеристики навыка после начисления XP.
  API умеет менять `attributeId`, но исторический XP остаётся в старой характеристике,
  а новые начисления идут в новую.
- [ ] Определить каскад при архивировании навыка. Активные шаблоны этого навыка продолжают
  создавать задачи, хотя сам навык скрыт из активных списков.
- [ ] Добавить связанную валидацию PATCH шаблона: для `weekdays` обязательны дни недели,
  при переходе на `daily` старый массив дней должен очищаться.
- [ ] Проверять реальную календарную дату, а не только формат `YYYY-MM-DD`, для задач,
  шаблонов и дедлайнов квестов. Значения вроде `2026-02-31` сейчас проходят Zod и падают
  позже на уровне даты или PostgreSQL.
- [ ] Разделить liveness и readiness. `/api/health` возвращает `ok` без проверки БД,
  поэтому контейнер считается здоровым при недоступном PostgreSQL.
- [ ] Добавить production-проверку обязательных переменных окружения. `DATABASE_URL`,
  `TELEGRAM_BOT_TOKEN`, allowlist и `APP_URL` остаются optional в общей env-схеме;
  ошибка обнаруживается только при первом реальном запросе.

## P1 — игровые механики и пользовательские сценарии

### Задачи и шаблоны

- [ ] Реализовать просмотр другой даты или запретить создание разовой задачи не на сегодня.
  Сейчас можно выбрать прошлую или будущую дату, после чего задача недоступна в UI.
- [ ] Реализовать редактирование и отмену/удаление задачи (`PATCH`/`DELETE /api/tasks/:id`),
  заявленные в `SPEC.md`. Статус `cancelled` в модели сейчас не используется.
- [ ] При редактировании задачи из шаблона добавить выбор «только эта задача» / «будущие
  задачи шаблона».
- [ ] Добавить полноценное управление шаблонами: редактирование, пауза, возобновление,
  просмотр расписания и архива. В профиле доступно только архивирование активного шаблона.
- [ ] Показывать описание и оценку длительности задачи. Поля есть в API/БД, но длительность
  отсутствует в форме, а описание не выводится в карточке.
- [ ] Решить, нужны ли отдельные базовые XP и сложность одновременно: пользователь вручную
  управляет обоими параметрами и может легко нарушить баланс.
- [ ] Унифицировать диапазоны XP: `SPEC.md`, UI-константы и API допускают разные пределы
  (`5–250`, `1–1000`, награда квеста до `10000`).

### Квесты

- [ ] Добавить редактирование и архивирование квеста в UI. PATCH endpoint существует,
  но пользовательского сценария нет.
- [ ] Вывести в форму квеста уже поддерживаемые моделью поля: характеристику, дедлайн,
  ручное/автоматическое завершение и обязательность шагов.
- [ ] Реализовать добавление, редактирование, удаление и сортировку шагов после создания
  квеста; вывести описание шага.
- [ ] Согласовать прогресс с необязательными шагами. Автозавершение учитывает только
  обязательные шаги, а progress bar считает все, поэтому завершённый квест может показывать
  меньше 100%.
- [ ] Связать шаг квеста с задачей дня. `tasks.quest_step_id` уже есть в схеме, но сценарий
  создания/выполнения такой задачи не реализован.
- [ ] Показывать характеристику и дедлайн квеста в списке и деталях после добавления этих
  полей в форму.

### Навыки и достижения

- [ ] Определить UX смены характеристики навыка: разрешать только до первого XP,
  переносить историю или полностью запретить.
- [ ] Подключить предусмотренные схемой `icon` и `color` либо удалить их из модели и
  спецификации как неиспользуемые поля.
- [ ] Показывать последствия отмены выполнения: уже открытые достижения остаются
  открытыми, хотя XP и серия откатываются.
- [ ] Сделать карточки достижений полезными на мобильном устройстве. Описание доступно
  только через HTML `title`, которого фактически нет в touch-интерфейсе.

### Прогресс и данные

- [ ] Согласовать смысл «XP за период»: сейчас учитываются только выполнения задач,
  а награды квестов видны в общем XP и журнале, но не входят в график и итог периода.
- [ ] Применять выбранный период к распределению по характеристикам либо явно подписать,
  что этот блок всегда показывает значения за всё время.
- [ ] Группировать три XP-транзакции одной задачи в одно понятное событие и показывать
  источник, название действия/квеста и дату. Сейчас журнал выглядит как несколько
  обезличенных начислений.
- [ ] Добавить импорт собственного JSON-экспорта и версионирование формата экспорта.
- [ ] Добавить массовый импорт контент-пака: навыки, повторяющиеся действия и квесты.
  Это позволит сначала генерировать и проверять контент в Markdown/JSON, затем загружать
  его без ручного заполнения каждой формы.
- [ ] Добавить проверку дубликатов и конфликтов при импорте контента.

## P1 — Telegram, тестирование и эксплуатация

- [ ] Проверить и выбрать стратегию cookie для Telegram Desktop/Web. `SameSite=Lax`
  может не работать внутри cross-site iframe; сейчас официально поддержан только основной
  мобильный сценарий.
- [ ] Синхронизировать тему с `Telegram.WebApp.colorScheme` и вызывать `expand()` при
  необходимости. Сейчас используется только системная тема браузера.
- [ ] Учесть верхний и нижний Telegram safe area не только в bottom navigation, но и в
  основном layout, Drawer и диалогах.
- [ ] Расширить E2E до сценариев из `SPEC.md`: создание навыка и повторения, выполнение и
  откат задачи, создание/прохождение квеста, статистика, запрет чужого пользователя.
  Сейчас E2E проверяет health, навигацию и создание разовой задачи через dev bypass.
- [ ] Добавить мобильный Playwright-проект и проверки ширины 320 px/safe area. Текущая
  конфигурация запускает только Desktop Chrome.
- [ ] Добавить отдельную проверку реального Telegram auth flow или максимально близкий
  браузерный fixture вместо покрытия E2E только через dev bypass.
- [ ] Автоматизировать off-site копирование бэкапов, проверку checksum, шифрование и
  регулярный тест восстановления. Текущий скрипт создаёт и ротирует только локальные копии.
- [ ] Добавить структурированные логи и минимальные метрики ошибок/латентности. Сейчас
  используются отдельные `console.error`, хотя `SPEC.md` требует структурированное логирование.
- [ ] Усилить CSRF-проверку в production: определить политику для запросов без `Origin`
  и при необходимости проверять `Sec-Fetch-Site`.
- [ ] Добавить CSP, совместимую с Telegram Mini App и внешним Telegram SDK, не ломая iframe.
- [ ] Добавить обслуживание таблицы сессий: удаление истёкших/отозванных записей.

## P2 — UX и доступность

- [ ] Вернуть пользователю конкретные ошибки API вместо одинаковых сообщений
  «Не удалось…» для валидации, конфликта и сетевой ошибки.
- [ ] Не отключать масштабирование страницы (`userScalable=false`) либо обосновать это
  отдельным accessibility-решением.
- [ ] Проверить минимальную touch-область 44×44 px. Часть кнопок и переключатели дней
  недели меньше требования из `SPEC.md`.
- [ ] Добавить `prefers-reduced-motion`/`motion-reduce` для Drawer, Dialog, progress bar
  и спиннеров.
- [ ] Сделать выбор часового пояса полным: UI предлагает только шесть зон, хотя backend
  принимает любую валидную IANA timezone.
- [ ] Обрабатывать ошибку сохранения темы: сейчас тема меняется локально до ответа API,
  а неуспешная запись никак не показывается.
- [ ] Сохранять ожидаемую позицию списков и состояние вкладок при возврате из деталей.

## P2 — документация и технический долг

- [ ] Синхронизировать `SPEC.md` с фактическим API: отсутствуют `/api/today` и
  `PATCH`/`DELETE /api/tasks/:id`, а часть реализованных ограничений не описана.
- [ ] Обновить roadmap-чекбоксы в `SPEC.md` или явно обозначить, что актуальный статус
  ведётся только в `TASKS.md`.
- [ ] Выпустить первую версию changelog вместо хранения всего MVP в `[Unreleased]`.
- [ ] Удалить устаревшие stage-комментарии в `env.ts`, `complete-task.ts` и schema-файлах.
- [ ] Добавить DB-level `CHECK`/enum-ограничения для статусов, типов, сложности и XP,
  чтобы целостность не зависела только от Route Handler и Zod.
- [ ] Решить политику уникальности пользовательских навыков и шаблонов, чтобы случайные
  дубликаты не размывали статистику и контент.

## Идеи контента

- [ ] Подготовить стартовый контент-пак по шести характеристикам: навыки, ежедневные и
  недельные действия, разовые задания и первые квесты.
- [ ] Описать единую шкалу XP по времени, усилию, дискомфорту и ценности результата.
- [ ] Добавить библиотеку шаблонов квестов: здоровье, обучение, работа, финансы,
  отношения, личные проекты.
- [ ] Добавить мягкий первичный выбор направлений, чтобы не создавать пользователю весь

  `SPEC.md` §5.9 только после стабилизации основного контента.
